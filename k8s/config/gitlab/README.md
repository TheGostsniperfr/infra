# GitLab

GitLab 19 from the official chart (`values.yaml`), with external PostgreSQL (`postgres-cluster`),
Redis (`redis.yaml`) and object storage (Garage). Every secret comes from Vault, generated by
Terraform (`terraform/secret_templates.tf`, section GitLab); the chart's shared-secrets job is
disabled so a rebuild gets the same keys back. Architecture: `architecture/gitlab/`.

| Host | What | Exposure |
|---|---|---|
| `gitlab.arffornia.com` | Web, API, Git over HTTPS | shared-gateway, Keycloak SSO |
| `gitlab-registry.arffornia.com` | Container registry | shared-gateway |
| `gitlab-kas.arffornia.com` | GitLab agent for Kubernetes (`wss://`) | shared-gateway |
| `gitlab-ssh.arffornia.com:5522` | Git over SSH | MetalLB `192.168.1.86`, router rule below |

## First install

1. Garage: create the key `gitlab-key` and the buckets `gitlab-lfs`, `gitlab-artifacts`,
   `gitlab-uploads`, `gitlab-packages`, `gitlab-terraform-state`, `gitlab-ci-secure-files`,
   `gitlab-dependency-proxy`, `gitlab-registry`, `gitlab-backups`, `gitlab-tmp`, each with
   read, write and owner for `gitlab-key` (commands in `k8s/config/garage-s3/README.md`).
2. Merge: the operator creates the role and database `gitlab`. GitLab waits for its secrets.
   The chart's upgrade check is a Helm pre-upgrade hook, which Argo CD also runs on the first
   sync. It reads the ConfigMap `gitlab-gitlab-chart-info`, which only exists after a sync, so
   the first sync loops on `unsupported upgrade path`. Create it once with the content the chart
   renders, Argo CD adopts it:
   ```sh
   kustomize build --enable-helm k8s/config/gitlab \
     | yq 'select(.kind=="ConfigMap" and .metadata.name=="gitlab-gitlab-chart-info")' \
     | kubectl apply --server-side --field-manager=argocd-controller -f -
   ```
3. Extensions: `amcheck` is not a trusted extension, so the `gitlab` role cannot create it.
   On the primary:
   ```sh
   kubectl exec -n postgres postgres-cluster-0 -- psql -U postgres -d gitlab \
     -c 'CREATE EXTENSION IF NOT EXISTS amcheck; CREATE EXTENSION IF NOT EXISTS btree_gist; CREATE EXTENSION IF NOT EXISTS pg_trgm;'
   ```
   Doc: https://docs.gitlab.com/administration/postgresql/extensions/
4. sops tfvars: `postgres_gitlab_user_var`, `postgres_gitlab_password_var` (from the secret
   `gitlab.postgres-cluster.credentials.postgresql.acid.zalan.do` in `postgres`),
   `gitlab_s3_access_key_var`, `gitlab_s3_secret_key_var`.
5. `terraform init` (new provider `hashicorp/tls`), then `terraform apply`.
   Root password: `kvv2/gitlab/root`. Sign in as root at `/users/sign_in?auto_sign_in=false`.
6. Check that `192.168.1.86` is free: `kubectl get svc -A | grep LoadBalancer`. Services without
   a pinned IP (like `postgres-lb`) take the first free one, which is how `.85` got lost.
7. Runner: Admin > CI/CD > Runners > New instance runner, copy the `glrt-...` token into
   `gitlab_runner_token_var`, `terraform apply`, then
   `kubectl rollout restart deploy/gitlab-gitlab-runner -n gitlab`.

## Router rule (Bouygues box) for Git over SSH

| Field | Value |
|---|---|
| Rule name | GitLab SSH |
| Protocol | TCP |
| External IP | empty |
| External port | 5522 |
| LAN device | `192.168.1.86` (typed as an IP: it is a MetalLB VIP, not a device) |
| Internal port | 5522 |

The same port is used inside and outside, so clone URLs work from the LAN, WireGuard and the
internet. sshd accepts keys only, user `git` only, no forwarding; a key is valid only when
attached to a GitLab account, and accounts come from Keycloak.

## Disaster recovery

State lives in four places: Vault (or the Terraform state, which holds the same values),
PostgreSQL (WAL-G), the Garage buckets and the Gitaly PVC (Git repositories). The Rails keys
in `kvv2/gitlab/rails` encrypt database columns: a database restore is unusable without them.
